到持续推进目标。

我关注目标、授权、长期状态与反馈如何进入 AI 产品。以下是基于五个个人作品提出的产品判断与待验证实验。

何时行动→理解个人→可靠执行→验证进步

可操作的产品取舍

现在，该主动吗？

场景：职业助手发现了一份更匹配的岗位，准备更新你的求职计划。

本地规则沙盘：不调用模型、不发送消息、不访问个人数据。它演示授权与状态如何改变动作选择。

    提示：有授权不等于必须立即执行。对外发送还需要明确收件人、材料版本与当前任务范围。

    1. 主动 Agent：把“何时不行动”也设计成产品能力

    一句话观点：主动性是行动时机的决策问题。系统需要在已授权目标下识别变化，判断是否值得打扰用户。

    主动 Agent 与 Personal Agent 是两条不同维度：主动描述何时发起行动，Personal 描述服务谁、保留怎样的长期上下文。企业销售 Agent 可以主动但不属于个人；个人问答助手可以个性化但始终被动。

    结合作品：SDR 已有人工确认的交互，千川已有校验与重试流程。这些可以继续发展为“事件 → 目标相关性 → 信息充分性 → 授权 → 时机与频控 → 建议/执行/等待”。

    具体场景：用户允许跟进养老方案，出现新的条款版本。系统先识别原方案受影响，再为顾问生成差异和提醒草稿；遇到证据不足或免打扰时，应等待或请求补充。不能仅凭停留五分钟就重复推销。

    关键取舍：评估预期收益时要同时考虑错误损失、打扰成本和执行成本。前期可以用明确规则做基线，等有真实标注后再学习触达策略。

    怎么验证：有效推进率、误触达率、用户关闭主动能力的比例、严重越权率；用同层客户的对照实验估计主动触达的增量。

    面试官可能追问：怎样证明不是规则提醒换了名字？

    我的回答：定时提醒可以是第一版。Agent 的价值应体现在根据目标和上下文选择不同动作，并用结果更新后续决策。如果任务固定、规则已经足够，就保留规则；只有需要动态判断与工具协作时才增加自主能力。

    2. Personal Agent：先解决长期目标与记忆治理

    一句话观点：个性化的关键是对持续目标、已完成任务和个人约束的可靠理解，记忆本身必须可查看、可更正、可过期。

    结合作品：从岗位知识库延伸为“个人职业成长助手”，下一步接入用户确认的职业目标、作品证据与练习记录，支持长期任务推进。

    具体场景：用户确认目标是金融 AI 产品经理，允许使用自己的项目和练习记录。岗位要求变化后，Agent 对照能力证据定位缺口，生成一周练习计划；只有在用户允许时提醒或写入日程，投递与对外沟通需要相应授权。

    记忆分层：稳定事实（经历、作品）记录来源；偏好（城市、方向）允许修改；进行中的目标有状态和截止时间；临时推断标注不确定性和有效期。一次回答失误不能永久写成“用户不会 RAG”。

    关键取舍：先做职业成长这个高相关领域，再讨论通用生活助理。共享长期状态有价值，也增加维护、隐私和错误传播成本。

    怎么验证：跨会话目标保持率、错误记忆率、修改删除生效率、建议采纳后的实际任务完成率。记忆条数和对话长度都不直接代表价值。

    面试官可能追问：为什么用户不直接用通用助手？

    我的回答：通用助手一定会覆盖更多基础能力。这个产品需要证明自己在岗位证据、学习反馈、行业标准和长周期任务推进上有独特积累。如果只是做一个聊天壳，差异化很容易被抹平。

    3. 企业 Agent 与个人 Agent：先明确为谁优化

    一句话观点：未来买卖双方都可能使用 Agent，产品必须说明自己的委托人、激励和信息来源。

    结合作品：SDR 与千川更接近企业销售与内容目标；职业成长助手服务求职者的长期目标。两种角色不能在没有说明的情况下共享同一套推荐目标。

    金融场景的判断：如果个人助手帮用户比较金融产品，而企业助手希望提高成交，两者可能有不同的优化方向。协议能帮助通信，却不能自动解决利益冲突、数据授权和适当性问题。

    下一步实验：先模拟“个人需求摘要 → 企业产品证据包 → 缺失条件澄清 → 用户确认”的协作。对比只优化成交的推荐与同时考虑用户约束的推荐，观察冲突如何暴露。

    怎么验证：约束满足率、证据完整率、利益冲突披露、授权范围内的数据使用、用户确认后的实际完成情况。

    面试官可能追问：Agent 商业化是否只能抽佣？

    我的回答：不一定。销售 Agent 可以按企业增量收益定价，个人 Agent 可以围绕订阅或完成服务收费。采用佣金模式时，需要处理推荐排序与用户利益的冲突；收费方式会反过来影响产品可信度。

    4. 模型升级：让控制框架能够做减法

    一句话观点：未来更强的模型可能接管一部分今天手写的规划和上下文处理，但权限、事件记录、结果校验与恢复能力仍需清晰接口。

    结合作品：SDR 的人工确认、千川的重试、照片生成的任务恢复，已经涉及不同的执行状态。下一步应该让目标状态、工具执行和记录彼此独立，而不是让某个 Prompt 成为全部系统的中心。

    关键取舍：不要把现有模型的每个弱点永久固化成复杂补丁。模型升级时，对同一任务集做对照，验证去掉某条编排规则后，质量、成本和稳定性是否改善。

    怎么验证：端到端任务成功率、失败恢复率、重复执行率、回滚成功率、每次成功任务成本。原始记录要能用于重建状态，摘要只负责提供当前上下文。

    面试官可能追问：模型越来越强，Harness 是否会消失？

    我的回答：具体补丁会变化甚至消失，但产品仍需定义目标、权限、运行状态与验收。我的投入重点是稳定的接口与评测，不是维护越来越大的 Prompt 和状态机。

    5. AI 自我优化：反馈必须经过可验证的闭环

    一句话观点：记录更多对话不会自动形成持续进步。需要把失败归因转成可验证的修改，并控制反馈污染。

    结合作品：销售 Agent 的 Trace 与千川内容重试提供反馈入口；下一步把 Badcase 分类到知识、检索、规划、工具、生成或交互，明确每类问题对应谁来修。

    流程设计：失败样本 → 归因与标注 → 提出修改 → 固定评测集与新增挑战集 → 小范围验证 → 监测与回滚。用户采纳不等于事实正确，短期转化也不等于长期用户收益。

    怎么验证：同时看最终环境状态、执行过程和交互质量。比如“已预约”要核对真实预约状态，“已完成封面”要检查产物存在且符合约束。分别维护能力评测与回归评测，防止优化新能力时破坏旧能力。

    面试官可能追问：大模型当裁判就够了吗？

    我的回答：可确定验证的结果用代码或系统记录；开放表达用经过人工校准的模型评分；高风险内容由专家抽检。评分器也会犯错，所以需要检查人与评分器的一致性，不能只看一张总分表。

    6. 多模态与空间 AI：从展示进入环境反馈

    一句话观点：多模态带来的机会不仅是更丰富的输出，而是让 Agent 获得不同形式的环境信息，并检验行动后发生了什么。

    结合作品：Photo to 3D 提供空间探索与碰撞反馈，是理解空间交互的实践，不应声称已经训练了世界模型。

    下一步实验：先在可控场景中做“理解用户目标 → 规划路线 → 检测可行走区域 → 到达并确认”的任务，再加入遮挡、失败恢复与人接管。视觉资产生成与因果环境建模是不同能力。

    怎么验证：目标到达率、碰撞率、状态判断正确率、失败后恢复率与跨场景泛化。视觉逼真不等于物理正确，更不等于任务成功。

    面试官可能追问：为什么产品经理需要碰空间项目？

    我的回答：它迫使我把“模型看起来理解了”转成“用户能否完成动作”的判断。这个经验同样适用于销售、求职和内容工具：最终需要用可观察结果检验能力。

    可以反问面试官的问题

    • 团队更希望 Agent 完成一个任务，还是持续负责一个业务目标？这两种授权与评测设计不同。
    • 哪些错误可以重试，哪些错误必须在执行前阻断？谁负责最终验收？
    • 今天最有价值的上下文来自哪里？数据与反馈能否进入后续迭代？
    • 模型升级后，团队会重新验证哪些自研模块还有保留价值？
    • 如果业务指标改善，但用户越来越不愿意授权，团队会怎样判断产品健康度？

    一手资料与判断边界

    • Anthropic：Building effective agents ↗：区分预定义工作流和动态 Agent，支持从简单方案起步。
    • Anthropic：Effective context engineering ↗：上下文是需要持续管理的有限资源。
    • Anthropic：Managed Agents ↗：将会话记录、控制循环和执行环境分离，并指出模型变化会使部分控制假设过时。
    • Anthropic：Demystifying evals for AI agents ↗：区分执行记录与环境最终状态，结合多类评分方法。
    • Google DeepMind：Project Astra ↗：展示记忆、多模态和工具能力在通用助手方向上的探索。
    • Google：A2A 协议 ↗：提供跨 Agent 协作的技术方向；协议出现不等于商业利益和信任问题已解决。
